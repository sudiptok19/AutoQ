# Independent AutoQ acceptance reproductions

Run this evidence bundle against a pinned, detached AutoQ checkout. The fixtures use synthetic inspections, synthetic seals and disposable database records generated by the candidate's existing test helpers and demo seed. The suite does not use a laptop backup or a retained phone.

## macOS setup

From an existing AutoQ clone, install Python 3.12, uv, Node.js 22, and a running local Docker Desktop. Keep the runner checkout separate from the candidate so the same runner can check multiple versions.

```sh
git fetch origin pull/44/head
git worktree add --detach ../autoq-acceptance-suite FETCH_HEAD

# Baseline with the expected failures below. Substitute the corrected full SHA for release verification.
CANDIDATE=5dfad857035b68f7a597dffc5d2cf03a51aea235
git worktree add --detach ../autoq-candidate "$CANDIDATE"
(cd ../autoq-candidate/backend && uv sync --locked)
npm --prefix ../autoq-candidate/frontend ci
npm --prefix ../autoq-candidate/e2e ci
(cd ../autoq-candidate/e2e && npx --no-install playwright install chromium)
docker pull postgres:16-alpine

RUN=../autoq-acceptance-suite/datasets/acceptance/run.py
python3 "$RUN" --checkout ../autoq-candidate --candidate "$CANDIDATE" --check-only
python3 "$RUN" --checkout ../autoq-candidate --candidate "$CANDIDATE" --group backend
python3 "$RUN" --checkout ../autoq-candidate --candidate "$CANDIDATE" --group diagnose
python3 "$RUN" --checkout ../autoq-candidate --candidate "$CANDIDATE" --group browser
```

Use `--case 'explicit_null or request_is_bounded'` with a backend group to run a focused smoke check. Use `--group keys` on a candidate that includes PR #43, such as `8e8a60c647f3dc80bb7a1519c8de9cd2fae4021b`. It runs the existing token, AQ1 interop and offline scanner tests. The known-failing baseline intentionally produces a nonzero exit from the backend group.

On Windows PowerShell, use `python` for the runner, set variables with `$Candidate = '…'` and `$Run = '../autoq-acceptance-suite/datasets/acceptance/run.py'`, and run the two directory-scoped dependency commands with `Push-Location` and `Pop-Location`. The runner resolves the candidate's Python with uv. Optionally pass `--python <candidate Python executable>` for an already installed candidate environment.

## Disposable preflight

The runner checks the candidate's full SHA, tree, detached HEAD, tracked cleanliness and absence of local dotenv files. It selects a local Docker context and creates one new PostgreSQL container per database run, with a random name, loopback port, password and run marker. It never mounts a database volume or accepts a caller-provided database URL. Before any destructive fixture runs, a read-only query must confirm the marker. The browser group also uses temporary signing material, an evidence directory, a fresh Chromium profile and dedicated loopback services.

The candidate must still expose the test helpers, API routes and browser seed used by these scenarios. In particular this suite uses the candidate's `backend/tests/conftest.py`, `test_chain_v2.py`, `test_offline_release_blockers.py`, dispatch/packing helpers, and the synthetic shipment that `backend/scripts/e2e_database.py` seeds. If a corrected candidate changes those interfaces, adjust the adapter or fixture with Opus and keep the corresponding release assertion.

## Baseline and release criteria

Candidates `769c003` and `5dfad85` share tree `a75f7715c65a4a0465aba74ec5ae8d18ff96cd7e`. The new runner packages the previously observed cases. The following cases are expected to **fail** on that baseline and **pass** on the corrected candidate.

| Backend test suffix | Observed baseline result | Required corrected behavior |
| --- | --- | --- |
| `departure_requires_a_nonempty_current_manifest` | Departure returned 200 after the last load was removed from the closed shipment | Refuse departure and persist zero departure movements |
| `departure_rechecks_seal_age` | Departure returned 200 with the most recent INTACT recheck older than the active maximum | Refuse departure and persist zero departure movements |
| `recovery_requires_reconciliation_type_evidence` | Unrelated synthetic evidence completed recovery | Leave recovery unsettled until attributable physical disposition is recorded |
| `refresh_keeps_requested_recovery_unsettled` | Refresh marked a pending recovery SUPERSEDED | Preserve the outstanding recovery and its task |
| `cross_shipment_snapshot_claim_stays_unvalidated` | Conflict was recorded with the wrong shipment's snapshot in the validated reference | Keep the submitted claim, leave the validated reference empty, and create no load |
| `ingress_preserves_explicit_null_distinction` | API accepted omitted v2 ONLINE snapshot as null | Reject the omission without advancing the checkpoint. Accept an explicit null ONLINE declaration |
| `policy_floor_cannot_be_lowered_after_cutover` | Ordinary policy publication lowered floor 2 to 1 | Reject the change and preserve the active floor |
| `legacy_drain_while_writer_is_v2_cannot_authorize_load` | A first-time v1 provisional event created a load with writer 2/floor 1 | Retain the event as a conflict with a task and zero new loads. Preserve exact historical replay |
| `alert_must_reference_the_target_spc_inspection` | Creation returned 201 with an unrelated alert | Require a persisted SPC warning linking that alert to the target inspection |

The browser group covers 201 v2 events. It loses the second request before submission, loses the next reply after the server commits, then retries. The final result must retain the same conflict and task, preserve the terminal chain head and both legitimate loads, and clear all pending events. The diagnostics group covers both transaction orders for settlement/close and recall/departure. It checks the full load before starting the race and records the gate output for the original recall setup. The historical retry 409 and blocked recall fixture did not recur.

Source-review items still require separate runtime tests. These include concurrent scan-ID adoption, the instruction for a late conflict after departure, migration of older reason-only recoveries on active shipments, and strict raw JSON member and integer decoding. The retained Vivo and physical disposition remain separate acceptance steps.

## Permanent placement

Opus owns integration of the backend assertions into the current offline, dispatch, recall and SPC suites, and the browser case into the mounted scanner E2E suite. This bundle is an independent, opt-in baseline. It is outside default test discovery and carries no plant runtime records.

The [PR #45 review](PR45_REVIEW.md) records the new two-step recovery, race and historical replay cases. The `r2` selector targets only those additional cases.
